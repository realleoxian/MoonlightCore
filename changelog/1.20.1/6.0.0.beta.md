# MoonlightCore | 6.0.0-beta
MoonlightCore 6.0.0 now uses a 'Runtime' platform implementation for environment variables
and for the mod layers. Now to use any of these utilities you must use the `MoonlightCore` methods,
including initializing the Common mod initializer. Or if you are using the client utilities, use
the `MoonlightCoreClient` class

This mod it's currently on beta, and it's susceptible to changes, removals, and errors. If you find
any error using this mod, please report it on the [GitHub repository](https://github.com/realleoxian/MoonlightCore/issues)

## Platform
- `EnvironmentSide` was renamed to `EnvSide `
- `PlatformEnvironment` was replaced by `MoonlightCoreRuntime` and `MoonlightCoreClientRuntime`
- 
- `Event` was renamed to `EventBus`
- `EventFactory` was removed and factory methods are inside `EventBus`


- `ChunkEvents` was renamed to `ChunkDataEvents`
- `EntityEvents` was replaced with `LivingEntityEvents`
- `PlayerEvents` was replaced with `ServerPlayerEvents`
- `RegisterCommandsEvent` was replaced by `CommandsRegistrar`
- `BlockEvent` was fully removed
- `CommonLLifecycleEvent` was fully removed
- `DatapackRegistryCreationEvent` was fully removed
- `RegistryCreationEvent` was replaced by `RegistryInformationRegistrar`
- `RegisterEvent` was replaced by `RegistryHelper`
- `ServerLevelLifecycleEvent` was fully removed
- `TickEvent` got split in multiple events:
    * `ServerLevelTickEvents`
    * `ServerTickEvents`
    * `PlayerTickEvents`
    * `ClientLevelTickEvents`
    * `ClientTickEvents`
- `EntityEvent#ATTRIBUTE_CREATION` was removed and replaced by `EntityAttributeRegistrar`

## Attachment API
Now AttachmentHolder(s) must implement the `AttachmentHolder` interface (made it already for built-in attachment holders)
and AttachmentMaps can ge get calling `AttachmentMap#get`.

- Now for synced `AttachmentType`s these get a `AttachmentSyncHandler`

## Networking Layer
- `CustomPacket` got fully removed
- `StreamCodec` got removed and replaced with:
  * `PacketEncoder`
  * `PacketDecoder`
- Now the packets can be registered using `PacketType`
- Added a utility class for player tracking (`PlayerTrackUtils`)
- Added a utility interface called `NetworkSerializable` for things that can be sent with a packet
- `PacketDispatcher` was replaced by `NetworkHelper`
- To register a packet now you need to use a `PacketRegistrar`

Here an example of how use the new networking layer:

```java
// First we create out packet
public record ServerboundUpdateManaPacket(int mana) {
    public static final PacketType<ServerboundUpdateManaPacket> TYPE = new PacketType(new ResourceLocation("examplemod:update_mana"), ServerboundUpdateManaPacket::encodeToBuf, ServerboundUpdateManaPacket::decodeFromBuf);
    
    public static void handle(UpdateManaPacket packet, NetworkHelper.PacketContext<ServerGamePacketListenerImpl> context) {
        int mana = packet.mana();
        
        context.queueWork(() -> {
            Player player = context.player();
            player.setMana(mana); // Method for this example
        });
    }
    
    public static void encodeToBuf(MyPacket packet, FriendlyByteBuf byteBuf) {
        byteBuf.writeInt(packet.data());
    }
    
    public static MyPacket decodeFromBuf(FriendlyByteBuf byteBuf) {
        return new MyPacket(byteBuf.readInt());
    }
}
```
With that, the packet it's finished, now it needs to be registered:
```java
// On our mod initializer
public static void myModInitializer() {
    var networkHelper = NetworkHelper.get();
    setupPackets(networkHelper);
}

private static void setupPackets(NetworkHelper helper) {
    var registrar = helper.registrar("moonlightcore");
    registrar.serverbound(ServerboundUpdateManaPacket.TYPE, ServerboundUpdateManaPacket::handle);
}
```
And that its, the packet it's now registered! NetworkHelper now it's for packet sending and configure the `PacketRegistrar`s with the next methods:
- `clientOnly(String namespace)`: By default it's false
- `serverOnly(String namespace)`: By default it's false
- `handlerThread(HandlerThread)`: By default it's the `HandlerThread.NETWORK` thread
- `protocolVersion(String protocolVersion)`: By default it's `1`

## Registry Layer
Now the registry isn't being managed by events and has its own layer.

- `DatapackRegistryBuilder` was removed
- `LookupProvider` was removed
- `LazyRegistryEntry` was removed
- `RegistryEntry` was replaced by `DeferredObject`, that it's implemented by the platform
- `RegistryBuilder` was replaced with `RegistryInformation` and now doesn't return any registry instance
- `DeferredRegister` was replaced by `RegistryHelper.Registrar`

Instead, now to register new registries it's needed to use `RegistryInformationRegistrar` which takes `RegistrtInformation`s.
To get the previously created registries now you have to use `RegistryHelper#getRegistry`. Here an example from this mod's attachment registry:

```java
    public static final ResourceKey<Registry<AttachmentType<?>>> ATTACHMENT_TYPE = ResourceKey.createRegistryKey(new ResourceLocation("moonlightcore", "attachment_type"));

    private static Supplier<Registry<AttachmentType<?>>> attachmentTypesRegistry;

    public static void setupRegistries(RegistryInformationRegistrar registrar) {
        // We create the registry here
        registrar.register(RegistryInformation.create(MoonlightCoreRegistries.Keys.ATTACHMENT_TYPE).synced(true));
    }
    
    public static void setup(RegistryHelper registryHelper) {
        // We get the registry here
        attachmentTypesRegistry = registryHelper.getRegistry(Keys.ATTACHMENT_TYPE);
    }

    public static Registry<AttachmentType<?>> attachmentTypes() {
        return attachmentTypesRegistry.get();
    }
```

## Config API
The Config API got a lot of internal and external changes.
- `ModConfigSpec` got removed
- Now the data of the config it's managed by `LoadedConfig`
- The config keys are no longer managed by a `List` of `String` and instead now it's being managed by `ConfigKey`
- `ValueKey` got renamed to `ConfigProperty`
- `ValueSerializer` was renamed to `ConfigPropertyType`
- Now config property validators are managed by `ConfigPropertyValidator` implementations instead of just a `Predicate`
- Now the config data it's managed by the `ConfigSchema` class
- `ModConfigSpec$Category` got renamed to `ConfigSection`
- Now config properties can support required restart types (`NONE`, `GAME`, `WORLD`)
- Now config schemas are build with `ModConfig#configure`
- `ModConfig` takes the type, the id (which will define the filename) and the schema builder
- When creating a config schema it must call at the end `build` to check and freeze further modification

Here an example of the Config API:

```java
public class CommonConfig {
    // Here we create the instance of the config, it is automatically tracked to changes on the file.
    // the first parameter specifies the type of config, if it's marked as `SERVER` it will get synced with the clients that join to a server
    // then the second parameter it's the internal id of the config, and it will specify the name as '<namespace>.<path>.ezc;
    // and lastly, the schema builder that gives the data of the config
    public static final CommonConfig INSTANCE = ModConfig.configure(ModConfig.Type.COMMON, new ResourceLocation("examplemod", "common_config"), CommonConfig::new);
    
    public final ConfigProperty<Boolean> enableSomething;
    
    private CommonConfig(ConfigSchema.Builder builder) {
        builder.push("hello.world"); // This will create two categories, 'world', and it's parent 'hello'
        this.enableSomething = builder.comment("This should enable something, ig") // Here we add a comment line to the config description (if it contains '\n' it gets split on multiple lines)
                .gameRestart().translationKey("examplemod.config.enableSomething") // Here first it's marked that to change the value in runtime of this property the game must be restarted, then the translation key of the config it's defined
                .defineBoolean("enableSomething", () -> false); // And here we define the key of the property, and it's default value
        
        builder.pop(2); // Then we pop both sections
        builder.build(); // And finally we build this config to freeze further modification
    }
}
```

The configs made with this API get automatically tracked when these are registered (something made by the `ModConfig#configure` method)

## Permission API
A Permission API was added to the mod, using `PermissionHelper` now can be registered permission resolvers,
this being a layer abstraction that it's compatible with the Forge's Permission API, and with (optional)
compatibility with the `fabric-permission-api` mod (not required, but if used, it will use a compatibility layer with it)

## Client API changes

- Added `ClientCommandsRegistrar`
- `HudRenderEvent` was renamed to `GuiRenderEvent` and parameters `context` and `poseStack` got removed
- `KeyMappingRegistrationEvent` was replaced by `KeyMappingRegistrar`
- `LevelRenderEvent` not implemented yet
- `RegisterClientCommandEvent` was replaced by `ClientCommandsRegistrar`
- `RenderingEvents` was replaced by multiple registrars:
  - `BLOCK_COLOR_REGISTRATION` -> `BlockColorRegistrar`
  - `ITEM_COLOR_REGISTRATION` -> `ItemColorRegistrar`
  - `BLOCK_RENDER_TYPE_REGISTRATION` -> `ChunkRenderLayerRegistrar`
  - `RENDERER_REGISTRATION` got split into two registrar:
    - `BlockEntityRendererRegistrar`
    - `EntityRendererRegistrar`
  - `MODEL_LAYER_REGISTRATION` -> `ModelLayerRegistrar`
  - `PARTICLE_PROVIDER_REGISTRATION` -> `ParticleProviderRegistrar`

- Added and `ScreenShake` utility to add camera/screen shakes to the game more easily
- Added `ShaderRegistrar` to register modded core shaders

- Added `ModelEvents`:
  - `REGISTER_MODELS_LOCATION`: Used to register custom models to the ModelBakery, the first event of these that gets fired
  - `MODIFY_MODEL_ON_LOAD`: Fired when trying to get an `UnbakedModel` and modify the returned `UnbakedModel`
  - `MODIFY_BEFORE_BAKE`: Fired just before a model it's going to be baked
  - `MODIFY_AFTER_BAKE`: Fired just after an `UnbakedModel` gets baked
  - `AFTER_BAKING`: Fired after all models get baked, also be used to modify the models after all of them get baked. Also at this phase you can register your blockstate model modifiers to change block models
